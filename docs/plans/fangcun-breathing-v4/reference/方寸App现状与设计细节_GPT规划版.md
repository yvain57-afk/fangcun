## 1. 先读这一页

方寸已经有可运行的 iPhone 原生 App、配套 watchOS 工程、真实 HealthKit 数据链路和本地持久化。当前产品主线是：

## 2. 创始人的目标、偏好与已确定方向

以下来自产品讨论，应作为规划输入：

1. 希望做一个确实能帮助一部分人的产品，而不是漂亮但没有价值的呼吸计时器。
2. 功能性呼吸方法是起点，长期方向是结合身体资料和生活习惯，给出可理解的状态判断及可执行的缓释建议。
3. 用户需要明确结论，不接受长期停留在含糊、无法行动的提示。明确结论必须对应实际可支持的范围，不能以确定语气掩盖缺数据。
4. 不喜欢进入 App 就被要求从「绷着」等有限预设中挑状态；寻找标签会增加负担，且不一定贴合本人感受。
5. 喜欢轻松、温暖、活泼但安静的界面；不喜欢僵硬的仪表盘和单调、不合情景的角色动画。
6. 猫狗要有各自性格，也要能单独出现。保留已经认可的原画，不要再用不协调的几何图形重画。
7. 饮品记录应轻量，涵盖水、咖啡因、酒精、含糖饮料；未来希望结合步行、有氧、力量等运动资料理解一天的状态。
8. 保留用户记录、既有练习、显示偏好和权限边界；不因改版清库或强制重走引导。

### 版本演进，避免 GPT 读错方向

- 早期 Web 设计：三种压力情景切换，首页＋练习＋趋势，猫狗和版画视觉探索。
- M0–M3：平台能力、数据标准化、准备度、解释、存储、原生接入与同步基础。
- V2：体验、饮品剂量与关怀、业务情境动效深化。
- **V3：分数优先重做，是目前最新的已交付产品方向。** 保留 V2 的饮品、视觉、动作和记录能力，但不再把「有限线索」作为有可靠睡眠时的默认首页结论。

后续规划应从 V3 增量改进，不要默认恢复旧版，也不要把过去任务书里的后续阶段当成已经完成。

## 4. 当前原生信息架构与关键流程

### 4.1 底部导航

实际是 **今日 / 练习 / 设置**。早期 Web 单独 Trends Tab 不是当前原生导航。

### 4.2 今日页

从上到下：

1. 开口环品牌标志、「方寸 FANGCUN」、大小字号切换、深浅色切换及更多菜单。
2. 日期、状态类别、更新或重试信息。
3. 主卡片：今日/上次状态、整数分数 `/100`、等级、一条原因、所属评估日期/周期、小幅角色插画。
4. 一条突出主行动，例如「开始 2 分钟安静休息」或「开始 5 分钟呼吸」。
5. 实际指标摘要与「看看分数构成」。
6. 「今天喝了什么？」入口，进入复合饮品记录弹层。
7. 至多一条优先关怀，不堆多个提醒卡。
8. 一周节奏、新状态分历史及近期练习/感受相关内容。

**真实合成测试例子：** 睡眠 6 小时 15 分、目标 8 小时，没有可用心率成分时，首页显示 `78 /100 尚可`，理由是实际睡眠时长，主行动是两分钟安静休息。不是预先写死 78 的展示状态。

无可用输入时，有连接健康、同步、重试、恢复分析或补记睡眠等明确入口；不能展示 0 分或擅自说「正常」。

### 4.3 分数详情

默认解释「这一次究竟用了什么」：实际成分、成分分数、归一化权重。数据和模型说明按需展开，避免首屏塞满术语。

时间必须区分测量时间、查询时间与计算时间。睡眠所属周期不能混成「刚更新就刚测量」，旧睡眠不能一直称「昨晚」。

### 4.4 历史

7 / 28 天查看状态；点选日期看当日构成与快照。晚到数据、来源选择、目标调整等可能形成同周期修订。构成变了要说明，不能把成分增减造成的数值变化直接包装为「恢复提升」。

**本次源码发现的待核对点：** 今日的历史入口使用 `DailyStatusHistoryView`，设置中的「历史与趋势」仍可路由到 `ReadinessHistoryView`。这是确切的入口差异；是否构成用户实际困惑尚待走查。建议规划统一新旧历史的入口语义，不先删除旧记录。

### 4.5 练习与反馈

既有练习目录包括：

| 类型 | 现有时长/入口 |
| --- | --- |
| 生理性叹息 | 1 分钟；保留首页可达的 5 分钟直接入口 |
| 节律呼吸 | 3 / 5 分钟 |
| 冥想 | 5 / 10 分钟 |
| NSDR | 10 / 20 分钟 |
| 凯格尔 | 3 分钟，不自动作为压力缓释推荐 |
| 轻行动 | 两分钟安静休息、一分钟座位舒展等 |

呼吸全屏包含双吸一呼节拍、剩余时间、暂停/继续、退出确认和结束反馈。动作、音频、触感应共用节拍；不是让插画随意循环。退出语气平和，不羞辱、不制造连续打卡负担。

感受补充与练习反馈是可跳过的实际记录，不要求首页先选一个情绪标签。现有流程仍可能有可选标签，不应把「没有强制预设入口」误写成「产品完全没有标签」。

## 5. 状态分：现有规则与不能擅自改变的内容

以下是工程配置与参考样例，**未被验证为医学标准**。规划可以评估其产品含义；开发时不能未经确认偷偷换参数或改 golden fixtures。

### 5.1 等级与总分

| 分数 | 等级 |
| --- | --- |
| 85–100 | 良好 |
| 70–84 | 尚可 |
| 50–69 | 偏低 |
| 0–49 | 优先休息 |

可参与的原始权重：睡眠 `0.60`，HRV `0.25 × qH`，静息心率 `0.15 × qR`。只对符合条件的项重新归一化，再求加权结果。缺失维度排除，不补零；不拿人群平均值假装个人基线。

### 5.2 睡眠

- 目标默认 480 分钟，可配置范围 420–600 分钟。
- 时长分：`min(实际睡眠 / 目标, 1) × 100`。
- 连续性：只有真实且完整的清醒覆盖才参与，按睡眠占睡眠＋清醒时长的比例计算。
- 规律性：有至少 3 个历史周期才参与，最多参考 14 个周期，使用环形时钟比较，120 分钟偏差对应零分端点；可关闭。
- 睡眠内部默认权重：时长 0.70、连续性 0.20、规律性 0.10。缺少可信子项时在剩余项中归一化。

固定样例：

| 条件 | 结果及解释 |
| --- | --- |
| 375 分钟 / 480 分钟，仅时长可用 | 78，尚可 |
| 480 分钟，仅睡眠可用 | 可达 100，良好；不能解释为心血管指标也正常 |
| 45 分钟，被确认是有效主睡眠 | 9，不能为了分低改成未知 |
| 240 分钟＋成熟且近基线的心率成分 | 对应既定测试配置为 64，规律性关闭；不是任意 4 小时睡眠必得 64 |

### 5.3 HRV 与静息心率

HRV 使用确认睡眠窗口内的实际 SDNN，按来源建立个人基线，并处理干预时段。当前一个样本可以使用，但个人历史须满足最低要求；历史成熟度、样本数和小时覆盖共同控制权重。

- 个人基线回看 28 天；最少 3 天，14 天达到历史质量满值。
- `qH = min(历史天数/14,1) × min(样本数/3,1) × min(小时覆盖/2,1)`。
- 静息心率采用系统实际静息心率与逐来源历史，不依赖「必须同时存在睡眠」；`qR = min(历史天数/14,1)`。
- 使用稳健尺度，HRV 尺度下限 0.10、静息心率下限 3；异常高 HRV 的既定排除只影响该成分。
- 心率成分在基线附近名义分 85，有闭区间和异常输入保护，成分上限 95。完整公式以固定源码与参考实现为准。

只有 HRV、缺少有效睡眠窗口等场景不能凭空生成可用 HRV 分；可比的静息心率可独立成分评分。具体组合有固定回归。

### 5.4 新鲜度、修订与删除

- 周期 18 小时内作为当前；18–24 小时明确为上次状态；24 小时后进入过期历史逻辑。不能只到午夜就刷新身份或造一个新分。
- 睡眠完成初始化可先发布，不必等待全部指标。
- 查询失败不能悄悄移除已有有效成分并重算一个看似正常的新分。
- 输入指纹、模型版本、配置、来源与依赖关系参与修订；查询时钟变化本身不应冒充状态变化。
- 来源选择、目标变化、晚到输入、删除均有处理；旧快照保留合理历史，并对被删除数据依赖进行处理。
- 主睡眠识别、去重、稳定选源、增量读取、删除与逐来源基线是既有数据链路的一部分。

## 6. 建议怎样生成，当前还缺什么

已有主行动策略考虑：正在练习、严重不适提示、驾驶/不方便行动、是否明确不想呼吸、此前不适反馈、夜间、主动放松意图、分数等级和偏好。

示例：

- 有进行中练习 → 继续练习。
- 驾驶等约束 → 先到安全位置，不催促立即练习。
- 不想呼吸 → 安静休息；若也不适合休息 → 座位舒展。
- 夜间 → 较短的放松路线；**不改分数**。
- 良好且偏好呼吸 → 五分钟呼吸；其他正常可行动场景可进入两分钟休息。
- 无资料、分析关闭等由首页提供连接、同步或恢复分析动作。

夜间使用确认过的睡眠计划；没有计划时使用本地 22:00–06:00 回退规则。代码中的策略与首页门控共同决定结果，不能只读一条条件就概括所有路由。

**未完成的产品验证：** 这些动作是否确实适合用户、是否比固定呼吸入口更有帮助、是否存在过度建议休息、哪些反馈应影响下一次选择。目前不能由规则和测试通过得出答案。

## 7. 饮品记录与关怀

### 7.1 已有体验

- 约半屏高的轻弹层，水、咖啡、酒精、含糖饮料可以复合记录。
- 水快捷加 250 ml；支持增减和撤销上一笔。
- 可编辑体积、实际饮用时间、咖啡因剂量或每 100 ml 含量、酒精度等。
- 咖啡默认估算 140 mg / 杯，可配置；修改默认值只影响新记录，历史估算保留当时依据。
- 酒精克数依据体积 × 酒精度 × 0.789；未知含量保留未知。
- 含糖饮料有份数与可选糖克数，不能称为完整精确营养数据库。
- 区分全部饮品、非酒精水分和白水；含糖咖啡不会重复计算两次体积。
- 无记录只代表尚未记录，不自动判断没喝水或缺水。

### 7.2 关怀边界

最多呈现一条优先关怀；用户确认的水分参考目标可调整，不把默认参考值当成适合所有人的强制量，夜间不催补水，限制饮水条件优先。

现有咖啡因、饮酒提醒含固定时间窗和剂量阈值，例如睡前时间窗、滚动 24 小时总量与用户自定上限。这些是待校准产品规则，不应在规划材料中包装成已验证的个体化医学判断。

通知由用户选择开启；有每日/滚动 24 小时最多两条、至少四小时间隔、默认 21:30–09:00 及睡眠安静时段等节流；锁屏文案克制。真实设备最终送达仍待单独验证。

**饮品关怀目前是一条独立逻辑，不直接惩罚或奖励状态分。** 若未来要把饮品影响纳入模型，必须先明确证据、时间窗口、估算误差与用户解释，而不是简单「咖啡扣几分」。

## 8. 视觉系统：保留的方向与具体细节

### 8.1 品牌

「方寸」围绕内心的一小片空间、给自己留一点余地。当前标志是有呼吸缺口的环抱形，深蓝主体与少量暖橙结合，不是「方」字外面套方框。后者已被明确否定。

### 8.5 动效原则与实际行为

- 动画和业务绑定：成功保存水记录后才有回应，不能先动画再写入失败。
- 水记录可以出现轻点头/水位反馈；咖啡和酒精保持中性，避免「饮酒也鼓励庆祝」。
- 完成时有限次爪碰等回应；提前退出平和收束，不用伤心角色施压。
- 呼吸局部胸腹起伏与双吸一呼一致，脚尽量稳定；不要整只动物像气球拉伸。
- 不做持续摇尾、反复蹦跳、无业务意义的独立「再看一次」宠物表演面板。
- 后台、不可见、低电量、减少动态效果等场景降级为静态或轻淡入。
- 已有 standard / gentle / static 模式与减少动画选项。
- 常用按压反馈约 0.14 秒、缩放 0.97、透明度 0.84；状态切换约 0.18 秒，入场约 0.20 秒；降低动态效果时使用约 0.12 秒淡入。不要把这些 UI 过渡时间当作呼吸节拍。

## 10. 工程、存储与权限

### 10.1 技术架构

- iOS 原生 SwiftUI；Swift 6；iOS 18 / watchOS 11 部署线。
- `InnerBalanceCore` 为共享 Swift Package，承载类型、评分、规则与可重放测试。
- App 层接 HealthKit、SwiftData、本地 Codable/UserDefaults、音频/触感、WatchConnectivity。
- 原画有本地局部变形渲染，含 Metal 相关实现；不是重新用几何形状代替原画。
- 大体链路：数据提供与标准化 → 睡眠/心率特征 → 独立数值引擎 → 评估存储与 owner → 今日/详情/历史。
- Web 为 React / Tailwind / Framer Motion / Lucide / Vite 设计原型，主要使用 Mock 数据。

### 10.2 数据与兼容

专用 Insights 存储支持版本、快照、修订、依赖、日志/备份和失败恢复。已有 schema 使用可兼容的可选字段扩展；原有 SwiftData 用户记录继续保留。

不能通过清库解决迁移。旧准备度和新状态分身份要区分；不能把旧标签硬映射成百分制。来源/目标同时变化时有并发一致性保护；数据与增量游标应保持一致，不能「游标成功、数据未存」。

### 10.3 权限与外部服务

既有健康读取涉及睡眠、HRV、静息心率、运动、正念及心境等相应路径；部分既有流程可写正念/心境，Watch 另有训练权限相关路径。具体读写清单以 entitlement 和实际授权调用为准。

未新增在线 AI、新后端、分析遥测或账户体系。跨端仅增加协商过的最小 `score-v3` 摘要 DTO，不传原始健康样本；旧端处理为撤回旧摘要，不能伪装兼容。

## 12. 我认为下一轮规划必须面对的问题

以下是基于现状的判断和待验证假设，不是已经批准的开发需求。

### P0：把「分数有用」验证清楚

**问题一：状态分与心理压力容易被混同。** 产品长期愿景是压力缓释，当前输入更接近睡眠与生理恢复线索。只睡够时长即可出现 100 分，而本人仍可能焦虑。这个差距要先通过命名、解释、反馈和用户研究处理，不能靠加更多小数或更强断言解决。

**问题二：明确不等于精确。** 分数让人更容易理解，但 78 与 81 是否值得区别对待尚无验证。规划应说明用户在看到分数后能作出什么更好的决定；不要只优化圆环、渐变和升分动画。

**问题三：评价闭环还缺实测。** 已能记录练习与反馈，但没有证据证明建议提升真实舒适度或带来持续使用。建议先选择一个具体人群与生活时刻，小规模验证「看懂 → 愿意做 → 做完有帮助 → 下次愿意回来」。不要先声称留存和疗效已成立。

### P0：厘清实际交付与入口

- 补齐当前代码到 TestFlight 到真机的版本对应与验收。
- 走查今日和设置的新旧历史入口，保持旧记录可访问。
- 用实际小屏、大字号、深色和真实稀疏资料验证首屏；已有模拟器通过不足以证明「3 秒认知」。

### P1：让关怀更贴合个人，又不增加输入负担

- 用户想要的运动/饮品/睡眠综合理解还没有全部完成。应先确定哪些资料会改变建议，而不是把所有资料强行塞入总分。
- 步行、有氧、力量训练的时间和恢复窗口，可先改善解释和动作选择；是否修改评分另立证据与校准任务。
- 用轻量选择/可跳过补充表达「我今天不想呼吸」「我现在不方便」；避免重建强制状态问卷。
- 分清缺数据、没记录、真实为零、来源冲突，展示适当下一步。

### P1：角色增加情景辨识，而不是增加动画数量

现有风格可以保留。更值得讨论的是：等待资料、专注练习、完成、暂停、饮品保存、夜间安静时，用户是否一眼知道角色在陪什么。仅增加换姿势或循环摇尾不能解决这个问题。

### P2：再决定扩展

Watch 独立体验、Widget、Live Activity、更多习惯维度、账号同步与商业化都需优先级取舍。目标人群、付费意愿、商业模式和长期效果目前没有足够证据；不能把「全方位」直接翻译成一次开发十种新功能。
